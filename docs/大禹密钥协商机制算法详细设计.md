# 大禹密钥协商机制算法详细设计

## 1. 文档目的

本文从算法和协议状态的角度说明禹家终端与设备节点之间现行的密钥协商机制。内容以当前工程代码为准，重点描述以下问题：

- 通信双方如何生成和交换椭圆曲线公钥；
- 如何从 ECDH 共享秘密派生 AES 和 SM4 会话密钥；
- 为什么新密钥不能在收到公钥后立即生效；
- 多台设备的密钥如何相互隔离；
- MQTT 与 HTTP 如何复用同一套密钥状态；
- 设备重启、密钥不同步和连续解密失败时如何恢复；
- 当前机制能够提供什么安全属性，以及仍有哪些限制。

本文不介绍照明、空调、窗帘等业务功能。业务命令在本文中统一视为待保护的明文消息 `M`。

## 2. 设计目标

当前密钥协商机制需要满足以下目标：

1. 大禹与每台设备独立建立会话密钥，任意一台设备的密钥不能用于解密另一台设备的消息。
2. 一次 ECDH 协商同时派生 AES-GCM 和 SM4-GCM 所需的密钥，切换算法时不重新执行 ECDH。
3. MQTT 与 HTTP 只承担传输职责，协议切换不能改变会话密钥。
4. 新旧密钥切换期间不能因为双方生效时刻不同而立即失去通信能力。
5. 设备重启或双方状态失配后，系统能够退回引导密钥并重新协商。
6. 重复公钥、消息回显、缓存消息和并发处理不能导致同一会话被反复安装。

## 3. 符号与参数

| 符号 | 含义 |
| --- | --- |
| `D` | 设备唯一标识 `deviceId` |
| `d_D` | 大禹为设备 `D` 生成的 P-256 私钥 |
| `Q_D` | 大禹对应的 P-256 公钥 |
| `d_E` | ESP32 当前协商私钥 |
| `Q_E` | ESP32 当前协商公钥 |
| `Z` | ECDH 共享秘密 |
| `PRK` | HKDF-Extract 输出的伪随机密钥 |
| `K_AES` | 32 字节 AES-256-GCM 会话密钥 |
| `K_SM4` | 16 字节 SM4-GCM 会话密钥 |
| `K_static` | 协商前和恢复阶段使用的预置引导密钥 |
| `epoch` | 当前密钥代际标识；现有大禹实现主要使用 `0/1` 表示静态/动态状态 |

固定算法参数如下：

| 参数 | 当前取值 |
| --- | --- |
| 椭圆曲线 | NIST P-256，即 `prime256v1` / `secp256r1` |
| 公钥编码 | SEC1 未压缩点格式，65 字节 |
| 密钥派生 | HKDF-SHA256 |
| HKDF Salt | 双方约定的固定 16 字节常量 |
| AES 密钥长度 | 32 字节 |
| SM4 密钥长度 | 16 字节 |
| GCM IV 长度 | 12 字节 |
| GCM Tag 长度 | 16 字节 |
| GCM AAD | 空字节串 |

## 4. 分层关系

现有系统包含两层相互独立的安全机制：

1. 传输层安全：MQTTS 或 HTTPS 使用 TLS 保护网络连接。
2. 消息层安全：ECDH 派生的 `K_AES` 或 `K_SM4` 用于保护业务消息。

TLS 与 ECDH 消息加密不是替代关系。即使使用 MQTTS/HTTPS，业务负载仍以 AES-GCM 或 SM4-GCM 密文发送。反过来，即使调试时使用明文 MQTT/HTTP，消息负载本身仍可以是 GCM 密文。

协议从 MQTT 切换到 HTTP 时，只改变密文的承载路径，不重新派生密钥：

```text
同一个设备 D
    ├── MQTT: publish dayu/cmd/{D}
    └── HTTP: enqueue command for {D}

两条路径共同使用 Session[D].K_AES 和 Session[D].K_SM4
```

## 5. 每设备独立状态

大禹为每个 `deviceId` 保存一份独立状态：

```text
Session[D] = {
    localKeyPair,
    localPublicKey,
    remotePublicKey,
    curveName,
    pendingAesKey,
    pendingSm4Key,
    pendingRemotePublicKey,
    established
}
```

运行时动态密钥表为：

```text
DeviceKeys[D] = {
    aesKey: K_AES,
    sm4Key: K_SM4
}
```

因此设备身份不是附加的显示字段，而是密钥选择算法的索引。发送命令时先根据能力绑定得到目标设备 `D`，再使用 `DeviceKeys[D]` 加密。接收消息时从 Topic 或 HTTP 报文中的 `deviceId` 得到 `D`，再使用同一项密钥解密。

必须满足以下不变量：

```text
EncryptKey = DeviceKeys[targetDeviceId]
DecryptKey = DeviceKeys[sourceDeviceId]
```

如果两台设备使用相同 `deviceId`，它们会竞争同一个状态槽，公钥、动态密钥和命令路由都可能互相覆盖。因此多设备系统必须保证 `deviceId` 唯一。

## 6. 公钥生成与编码

### 6.1 密钥对生成

大禹按设备创建 P-256 密钥对：

```text
d_D <- Random(1, n - 1)
Q_D = d_D * G
```

其中 `G` 是 P-256 基点，`n` 是基点阶。底层随机数和椭圆曲线运算由 OpenHarmony `cryptoFramework` 提供。

实现会依次尝试以下曲线名称，以兼容不同系统版本：

```text
NID_X9_62_prime256v1
prime256v1
secp256r1
```

这些名称指向同一条 P-256 曲线，不表示三种不同算法。

### 6.2 公钥线格式

公钥使用 SEC1 未压缩点格式：

```text
Q_raw = 0x04 || X || Y
```

其中：

- `0x04` 为未压缩点标记；
- `X` 为 32 字节大端坐标；
- `Y` 为 32 字节大端坐标；
- 总长度固定为 65 字节。

接收端首先检查：

```text
length(Q_raw) == 65
Q_raw[0] == 0x04
```

随后将 `X`、`Y` 转为大整数，并交给曲线库构造远端公钥。曲线库应继续负责点合法性检查，包括坐标范围和点是否位于曲线上。

## 7. 公钥交换

### 7.1 设备作用域 Topic

双方通过以下设备作用域 Topic 交换原始公钥：

```text
key/ecdh/pub/{deviceId}
```

MQTT 下，65 字节公钥作为二进制 Payload 直接发布。HTTP 下，公钥被 Base64 编码后放入命令队列，但从队列取出后仍按 65 字节原始公钥处理，不进入 GCM 解密流程。

公钥必须绕过业务密文解密。原因是首次协商时双方还没有动态密钥，65 字节公钥本身也不符合 `IV || TAG || Ciphertext` 的业务包语义。

### 7.2 发起方式

协商可以由任意一方先发布公钥。大禹也可以发送以下逻辑请求，让设备重新发布公钥：

```json
{
  "cmd": "key",
  "action": "pub",
  "deviceId": "目标设备编号",
  "source": "dayu",
  "seq": 1
}
```

正常情况下，大禹优先直接发布自己的公钥。只有直接发送失败或需要显式请求设备重发时，才使用上述命令。

### 7.3 回显和重复抑制

同一个 Topic 同时承载双方公钥，Broker 可能把大禹自己发布的公钥再次投递给大禹。系统通过两层判断抑制回显：

1. 发送公钥时记录近期发送值，接收时先与近期值比较；
2. `Session[D].localPublicKey` 与收到的字节完全相同则判定为自己的公钥。

已经建立会话后，如果收到的远端公钥与 `Session[D].remotePublicKey` 完全一致，则视为重复消息，不重新安装密钥。

字节比较采用累计异或方式：

```text
diff = 0
for i in [0, length):
    diff = diff OR (A[i] XOR B[i])
equal = (diff == 0)
```

该写法避免在第一个不同字节处提前返回，减少比较时间泄露。

### 7.4 时间与并发过滤

对同一 Topic，系统记录最近处理时间戳：

- 时间戳不大于已处理值的消息直接忽略；
- 一般缓存公钥超过 10 分钟即视为陈旧；
- 当本机没有该设备动态密钥时，允许使用 24 小时以内的缓存公钥进行恢复；
- 同一 Topic 正在处理时，新到达的并发公钥暂不重复处理。

## 8. ECDH 共享秘密计算

大禹收到设备公钥 `Q_E` 后执行：

```text
Z_D = ECDH(d_D, Q_E)
```

ESP32 执行：

```text
Z_E = ECDH(d_E, Q_D)
```

根据椭圆曲线 Diffie-Hellman 性质：

```text
Z_D = d_D * Q_E
    = d_D * d_E * G
    = d_E * Q_D
    = Z_E
```

双方因此得到相同的共享秘密，而私钥始终不通过网络发送。

### 8.1 共享秘密归一化

不同密码库可能省略大端整数开头的零字节，因此 ECDH 输出长度不一定始终表现为 32 字节。现有实现将共享秘密归一化为 32 字节：

```text
Normalize(Z):
    if len(Z) == 32: return Z
    if len(Z) > 32:  return last 32 bytes of Z
    if len(Z) < 32:  left-pad Z with zero bytes to 32 bytes
```

双方必须采用相同归一化规则，否则当共享秘密具有前导零时会派生出不同密钥。

## 9. HKDF-SHA256 密钥派生

ECDH 输出不直接作为业务密钥，而是输入 HKDF-SHA256。这样可以把一个共享秘密稳定地扩展为用途不同、长度不同的两把密钥。

### 9.1 Extract 阶段

设归一化后的共享秘密为 `Z`，固定 16 字节 Salt 为 `S`：

```text
PRK = HMAC-SHA256(S, Z)
```

### 9.2 Expand 阶段

HKDF Expand 的单轮形式为：

```text
T(0) = empty
T(i) = HMAC-SHA256(PRK, T(i-1) || info || byte(i))
OKM  = first L bytes of T(1) || T(2) || ...
```

当前派生两次，使用不同的 `info` 实现域分离：

```text
K_AES = HKDF-SHA256(Z, salt=S, info="aes-key", L=32)
K_SM4 = HKDF-SHA256(Z, salt=S, info="sm4-key", L=16)
```

即使两把密钥来自相同 ECDH 共享秘密，由于 `info` 不同，它们的输出也相互独立。不能通过截取 `K_AES` 的前 16 字节代替 `K_SM4`。

### 9.3 HMAC-SHA256

HMAC 使用 SHA-256 的 64 字节分组：

```text
K0 = PadOrHash(key, 64)
inner = SHA256((K0 XOR 0x36) || data)
HMAC  = SHA256((K0 XOR 0x5c) || inner)
```

大禹端当前在 ArkTS 中实现 SHA-256、HMAC 和 HKDF，以确保输出与 ESP32 端实现逐字节一致。

## 10. Pending Key 两阶段激活

### 10.1 为什么不能立即激活

假设大禹收到设备公钥后立刻切换为新密钥，但设备尚未收到大禹公钥，设备仍使用旧密钥。此时大禹发出的第一条新密钥消息设备无法解密，设备用旧密钥回复的消息大禹也可能拒绝，双方会进入失联状态。

因此现有机制采用“派生”和“激活”分离：

```text
收到远端公钥
    -> 计算 K_AES / K_SM4
    -> 保存为 pending key
    -> 保持当前 active key 不变
    -> 等待新密钥保护的 ACK
    -> ACK 验证成功后激活 pending key
```

### 10.2 Pending 状态

派生完成后：

```text
Session[D].pendingAesKey = K_AES
Session[D].pendingSm4Key = K_SM4
Session[D].pendingRemotePublicKey = Q_E
```

此时 `Session[D].established` 尚未更新，原有动态密钥或静态引导密钥仍是业务层 active key。

### 10.3 ACK 验证

设备安装新密钥后，应使用新密钥发送确认消息。大禹在常规解密之前，优先尝试用 pending key 解密到达的数据：

```text
for mode in [当前算法, 另一个算法]:
    K = pending key corresponding to mode
    P = GCM_Decrypt(K, packet)
    if P is valid key ACK:
        activate pending keys
```

标准确认消息满足：

```text
type == "ack"
cmd  == "key"
ok   != false
```

为了兼容设备端早期实现，当前大禹代码还允许：只要 pending key 能通过 GCM Tag 验证，并解出一个合法 JSON 对象，也可视为设备已经使用新密钥，随后激活 pending key。这个分支称为 observed activation。

GCM Tag 验证使随机错误数据几乎不可能被误认为有效密文，但从协议严格性看，显式 `key ACK` 仍是推荐方式。

### 10.4 激活操作

确认成功后执行原子式状态迁移：

```text
Session[D].remotePublicKey = pendingRemotePublicKey
Session[D].established = true

DeviceKeys[D].aesKey = pendingAesKey
DeviceKeys[D].sm4Key = pendingSm4Key

clear pendingAesKey
clear pendingSm4Key
clear pendingRemotePublicKey
```

随后清除该设备的解密失败计数和等待状态，并记录安装时间。当前设备的界面状态更新为：

```text
keySource = dynamic
epoch = 1
```

## 11. 完整时序

```text
大禹                                               设备 D
  |                                                   |
  |  生成 d_D, Q_D                                    |
  |                                                   |
  |--- Q_D, key/ecdh/pub/{D} ----------------------->|
  |                                                   | 生成 d_E, Q_E
  |                                                   | 计算 Z_E
  |                                                   | 派生 K_AES, K_SM4
  |<-- Q_E, key/ecdh/pub/{D} ------------------------|
  |                                                   |
  |  校验 65B 公钥                                    |
  |  计算 Z_D                                         |
  |  派生 pending K_AES, pending K_SM4                |
  |                                                   |
  |<-- GCM(K_pending, key ACK) -----------------------|
  |                                                   |
  |  pending key 解密与 Tag 验证成功                  |
  |  pending -> active                                |
  |  持久化 DeviceKeys[D]                             |
  |                                                   |
  |--- GCM(K_active, business command) -------------->|
  |<-- GCM(K_active, status or ACK) ------------------|
```

双方公钥到达顺序可以相反，算法结果不受影响。关键约束是：发送新密钥 ACK 的一方必须已经收到对端公钥并完成相同的 HKDF 派生。

## 12. 业务消息加密格式

AES-GCM 和 SM4-GCM 使用统一线格式：

```text
Packet = IV || TAG || CIPHERTEXT
```

字段长度为：

```text
IV         12 bytes
TAG        16 bytes
CIPHERTEXT N bytes
```

每次加密重新生成随机 12 字节 IV，AAD 为空。对于同一把 GCM 密钥，IV 不得重复。解密流程为：

```text
iv  = Packet[0:12]
tag = Packet[12:28]
ct  = Packet[28:]
M   = GCM_Decrypt(K, iv, ct, aad=empty, tag)
```

只有 Tag 验证成功后才输出明文。Tag 不匹配、包长小于 28 字节或 UTF-8/JSON 解析失败都不能作为有效业务消息处理。

## 13. 加密算法切换

一次 ECDH 协商同时得到 `K_AES` 和 `K_SM4`，因此算法切换只改变密钥选择，不改变 ECDH 会话：

```text
mode == AES -> use DeviceKeys[D].aesKey
mode == SM4 -> use DeviceKeys[D].sm4Key
```

切换命令必须使用“切换前”的当前会话加密。收到设备切换 ACK 后，大禹才更新该设备的算法状态。

接收端在正常情况下先按设备记录的算法解密。若失败，会尝试兼容路径：

1. 当前算法、当前设备动态密钥；
2. 当前算法、静态密钥；
3. 另一算法、静态密钥；
4. 另一算法、当前设备动态密钥。

如果另一算法和动态密钥解密成功，系统可自动校正该设备的算法记录。算法切换刚发生或切换 ACK 尚未完成时，自动校正会被短暂抑制，避免旧消息让界面在 AES 与 SM4 之间反复跳转。

## 14. 静态引导密钥与动态会话密钥

当前实现包含两类密钥：

### 14.1 静态引导密钥

静态 AES 和 SM4 密钥预置在两端，主要用于：

- 首次 ECDH 前的引导通信；
- 设备重启后恢复到已知状态；
- 动态密钥丢失后的重协商；
- 与旧设备固件兼容。

静态密钥状态表示为：

```text
keySource = static
epoch = 0
```

### 14.2 动态会话密钥

ECDH 和 HKDF 产生的设备独立密钥表示为：

```text
keySource = dynamic
epoch = 1
```

大禹端当前 `epoch` 更接近“静态/动态状态位”，并不是完整的单调递增密钥版本号。若后续需要可靠处理多轮主动轮换，应将 `epoch` 扩展为双方共同确认的递增整数，并把它纳入 ACK 校验和密钥存储索引。

## 15. 密钥持久化

动态密钥激活后，大禹按设备保存：

```text
Registry[D] = {
    aes: Base64(K_AES),
    sm4: Base64(K_SM4)
}
```

应用恢复时，只有长度同时满足以下条件才安装：

```text
len(Base64Decode(aes)) == 32
len(Base64Decode(sm4)) == 16
```

长度不合法的记录会被拒绝，并回到静态会话。

Base64 只是二进制编码，不提供加密保护。当前实现把密钥放在应用持久化存储中，能够解决应用重启后的会话恢复，但不能等同于硬件安全存储。生产化时应迁移到 OpenHarmony HUKS 等受保护的密钥存储，并限制日志输出敏感材料。

## 16. 设备重启处理

设备上报 boot 状态且表明：

```text
epoch = 0
keySource = static
```

大禹认为设备已经丢失动态会话，执行以下步骤：

1. 清除该 `deviceId` 的运行时动态密钥；
2. 删除该设备持久化动态密钥；
3. 清除本地 ECDH 密钥对和远端公钥记录；
4. 清理解密成功时间、失败计数和 pending 时间；
5. 将该设备状态切换为静态会话；
6. 延时发起新的 ECDH 协商。

为了避免迟到的旧 boot 消息破坏刚建立的动态会话，代码会结合 pending 状态、新近密钥安装时间以及 boot 签名去重，忽略明显陈旧的 `epoch=0` 状态。

## 17. 连续解密失败恢复算法

每台设备分别维护失败计数 `FailCount[D]`。收到无法通过所有候选密钥和算法验证的密文时执行：

```text
FailCount[D] = FailCount[D] + 1
```

但以下情况不立即重协商：

- 6 秒内该设备曾成功解密，认为可能只是迟到包；
- pending key 已产生且等待 ACK 不超过 15 秒；
- 新密钥安装不超过 8 秒，处于切换宽限期；
- 失败次数少于 3 次；
- 同一设备已经在恢复中；
- 距离该设备上次恢复不足 20 秒。

只有全部条件通过后才执行：

```text
clear DeviceKeys[D]
switch D to static session
reset ECDH state for D
publish/request new public key
```

该算法通过阈值、时间窗和单设备互斥避免网络抖动或单个损坏包引发密钥协商风暴。

## 18. 红外学习期间的协商锁

空调红外 `learn-all` 最长持续数分钟，并在过程中连续返回多条 ACK。若中途更换密钥，后续 ACK 可能仍使用旧密钥，导致学习进度丢失。

因此当红外学习处于 active 或握手确认状态时，大禹暂停：

- 新的 ECDH 发起；
- 公钥发布；
- 公钥回复重试；
- 收到公钥后的处理；
- 因解密失败触发的自动恢复。

学习结束后才能继续协商。这不是密码算法本身的要求，而是长事务期间保持会话一致性的工程约束。

## 19. MQTT 与 HTTP 下的等价性

密钥协商层只接收以下抽象输入：

```text
(topic, rawPublicKey, timestamp)
```

它不关心输入来自 MQTT 订阅还是 HTTP 轮询。

MQTT 路径：

```text
Broker publish -> topic + 65B payload -> KeyExchangeLayer
```

HTTP 路径：

```text
HTTP command queue -> payloadBase64 -> Base64 decode
                   -> topic + 65B payload -> KeyExchangeLayer
```

业务密文同样先还原为 `Uint8Array`，再进入统一 GCM 解密流程。由此得到两个重要结论：

1. MQTT/HTTP 切换不应重新生成密钥；
2. HTTP Bridge 不应自行选择另一把密钥或重新加密已经生成的业务密文。

## 20. 核心伪代码

### 20.1 收到远端公钥

```text
OnRemotePublicKey(D, P):
    require len(P) == 65 and P[0] == 0x04
    if P == recentlySentLocalKey: return
    if P == Session[D].localPublicKey: return
    if Session[D].established and P == Session[D].remotePublicKey: return

    if Session[D].localKeyPair is empty:
        Session[D].localKeyPair = GenerateP256KeyPair()

    SendPublicKey(D, Session[D].localPublicKey)

    Z = Normalize32(ECDH(Session[D].privateKey, P))
    pendingAes = HKDF_SHA256(Z, fixedSalt, "aes-key", 32)
    pendingSm4 = HKDF_SHA256(Z, fixedSalt, "sm4-key", 16)

    Session[D].pendingAesKey = pendingAes
    Session[D].pendingSm4Key = pendingSm4
    Session[D].pendingRemotePublicKey = P
```

### 20.2 收到加密消息

```text
OnEncryptedPacket(D, packet):
    if Session[D] has pending keys:
        for mode in [expectedMode(D), otherMode]:
            if GCM_Decrypt(pendingKey(D, mode), packet) succeeds:
                if plaintext is key ACK or valid JSON object:
                    ActivatePending(D)
                    return plaintext

    try active device key with expected mode
    try static key with expected mode
    try static key with other mode
    try active device key with other mode

    if all attempts fail:
        HandleDecryptFailure(D)
```

### 20.3 发送业务命令

```text
SendCommand(targetDeviceId D, plaintext M):
    mode = CryptoMode[D]
    if DeviceKeys[D] exists:
        K = DeviceKeys[D][mode]
    else:
        K = StaticKey[mode]

    iv = SecureRandom(12)
    (ciphertext, tag) = GCM_Encrypt(K, iv, M, aad=empty)
    packet = iv || tag || ciphertext

    route packet by Transport[D]
```

## 21. 正确性条件

一次协商成功要求双方以下输入完全一致：

1. 使用同一条 P-256 曲线；
2. 公钥坐标按 32 字节大端格式编码；
3. ECDH 输出按相同规则归一化为 32 字节；
4. HKDF Salt 完全一致；
5. `info` 字符串严格为 UTF-8 编码的 `aes-key` 和 `sm4-key`；
6. AES 输出取 32 字节，SM4 输出取 16 字节；
7. ACK 使用刚派生出的 pending key 加密；
8. 消息格式严格为 `IV(12) || TAG(16) || Ciphertext`；
9. 双方对同一设备使用相同且唯一的 `deviceId`。

任何一个字节不一致，最终表现通常都是 GCM Tag mismatch，而不是可读的“密钥派生错误”。因此联调时应按上述顺序逐层比对，而不是直接更换 AES 或 SM4 实现。

## 22. 安全属性

在公钥来源可信、随机数可靠且私钥未泄露的前提下，当前机制能够提供：

- 密钥机密性：私钥不通过网络发送；
- 每设备隔离：不同 `deviceId` 使用不同 ECDH 状态和动态密钥；
- 算法域分离：AES 与 SM4 使用不同 HKDF `info`；
- 消息机密性：业务明文由 GCM 加密；
- 完整性与来源持有证明：只有持有对应密钥的一方才能生成有效 GCM Tag；
- 一定程度的前向保密：若每轮协商都生成新的临时 ECDH 私钥，后续静态引导密钥泄露不会直接恢复过去的动态密钥。

## 23. 当前安全边界与改进方向

### 23.1 公钥未做数字签名

当前公钥交换本身没有证书、签名或预共享密钥 MAC。若运行在无 TLS 的不可信网络中，主动中间人可以分别与大禹和设备建立两个 ECDH 会话。

现阶段应默认使用 MQTTS/HTTPS，并正确校验证书。后续可在 ECDH 公钥上增加设备身份签名，或使用预共享引导密钥对以下内容计算 HMAC：

```text
deviceId || publicKey || nonce || epoch
```

### 23.2 静态回退密钥是全局预置值

静态密钥用于兼容和恢复，但一旦同型号设备共享同一预置值，任意一台设备固件泄露都可能影响其他设备的引导阶段。

更稳妥的方案是每台设备出厂写入不同的引导密钥，配网时由大禹建立设备级信任关系。

### 23.3 动态密钥以 Base64 持久化

Base64 不提供保密性。应将动态密钥移入 HUKS 或等价的系统密钥库，持久化层只保存不可导出的密钥句柄。

### 23.4 调试日志可能输出敏感材料

当前 `KeyExchangeLayer` 的调试日志包含共享秘密和派生密钥的十六进制值，这有利于联调，但不适合发布版本。生产构建应完全移除以下日志：

```text
ECDH shared secret
pending AES key
pending SM4 key
```

### 23.5 epoch 不是完整版本号

目前大禹主要用 `epoch=0/1` 区分静态和动态密钥，不能严格区分第 1、2、3 次动态协商。建议后续把 epoch 改为单调递增值，并将其加入：

- 公钥认证数据；
- key ACK；
- 设备状态；
- 持久化会话记录；
- 消息 AAD。

### 23.6 GCM AAD 为空

当前 GCM 只认证明文，不认证 Topic、设备编号、算法和 epoch。若密文被错误路由，通常会因设备密钥不同而失败，但协议本身没有把路由元数据绑定到密文。

后续可定义：

```text
AAD = version || deviceId || topic || mode || epoch || seq
```

这样可防止跨 Topic 重放和元数据替换。

### 23.7 缺少明确的重放窗口

随机 IV 和业务 `seq` 能降低重复消息影响，但当前密钥层没有统一维护已接收 IV 或序列号窗口。对开锁、撤销报警等敏感命令，应在设备端按 `deviceId + epoch + seq` 执行去重。

## 24. 联调校验顺序

当双方出现“都无法解密”时，建议按以下顺序记录并比对，不要同时改动多个环节：

1. 确认 Topic 中的 `deviceId` 与设备真实 ID 一致；
2. 确认双方收到的公钥均为 65 字节且首字节为 `0x04`；
3. 比较双方公钥 `X`、`Y`；
4. 比较归一化后的 32 字节共享秘密；
5. 比较 HKDF Salt；
6. 比较 `aes-key` 派生出的 32 字节值；
7. 比较 `sm4-key` 派生出的 16 字节值；
8. 确认 ACK 使用 pending key，而不是旧动态密钥或静态密钥；
9. 确认 Payload 布局为 `IV || TAG || Ciphertext`；
10. 确认 MQTT/HTTP Bridge 没有二次加密、截断或错误路由；
11. 确认同一时刻没有另一块设备使用相同 `deviceId`；
12. 确认红外学习期间没有触发新的 ECDH。

## 26. 总结

当前密钥协商机制可以概括为：

```text
按 deviceId 建立独立 P-256 ECDH 会话
    -> 归一化 32 字节共享秘密
    -> HKDF-SHA256 分别派生 AES-256 和 SM4 密钥
    -> 新密钥先进入 pending 状态
    -> 使用 pending key 验证设备 ACK
    -> 确认后原子激活并按设备持久化
    -> MQTT/HTTP 共享同一会话
    -> 连续解密失败后回退静态引导密钥并重新协商
```

这一设计已经解决了多设备密钥串用、切换时序和通道切换导致的主要同步问题。下一阶段若面向正式部署，优先级最高的改进是公钥身份认证、设备级引导密钥、安全密钥存储、敏感日志移除，以及将 epoch 和 AAD 纳入完整协议定义。
