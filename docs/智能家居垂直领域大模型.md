# 智能家居垂直领域大模型

## 1. 名称与定位

本文档用于梳理 DAYU 智能终端中的自然语言理解模块。对外汇报时可以称为“智能家居垂直领域大模型”，因为它面向智能家居垂直场景，能够把用户语音转成可执行的结构化意图，并与后续规划器、安全执行链联动。

需要注意的是，它不是通用聊天大模型，也不是云端通用问答模型。当前技术本质是：

```text
中文预训练 Transformer 底座
  + 智能家居垂直领域数据集监督微调
  + 分层意图分类
  + 确定性槽位解析
  + 安全规则与规划器约束
  + DAYU 本地 ONNX 推理部署
```

这样做的好处是模型小、可离线运行、可控性强，适合 DAYU 端侧设备。它负责“理解用户在智能家居里想做什么”，不负责自由聊天，也不直接绕过业务层控制设备。

## 2. 项目目标与边界

本模块的目标是把唤醒后的 ASR 文本解析成统一的智能家居结构化指令，支持明确控制、状态查询和抽象需求。

当前边界如下：

| 模块 | 作用 | 是否属于本文 NLU |
| --- | --- | --- |
| 唤醒词检测 | 识别“小禹小禹” | 否 |
| ASR | 把语音转成文字 | 否 |
| NLU | 把文字转成意图、槽位、目标 | 是 |
| 规划器 | 把抽象需求转成动作计划 | 配合 NLU，但不是 NLU 本体 |
| 安全执行链 | 校验动作是否合法、是否可执行 | 配合 NLU，但不是 NLU 本体 |
| 联邦 MLP | 根据家庭行为和传感器特征预测抽象需求 | 独立模块，不属于语音 NLU |
| DAYU MQTT Broker | DAYU 本机和 ESP32 通信 | 执行层，不属于 NLU |
| PC Broker | 上传数据、训练流程使用 | 训练侧，不是 DAYU 设备控制链路 |

本文档只描述 NLU 与它的接口关系，不修改联邦学习模块。

## 3. 端到端链路

当前 DAYU 语音链路可以概括为：

```text
麦克风
  -> 唤醒词“小禹小禹”
  -> 本地流式 ASR
  -> 可选声纹校验
  -> 硬安全规则和领域规则
  -> 确定性规则解析
  -> 分层 Transformer NLU
  -> 槽位提取与范围复核
  -> DAYU 执行层或 Planner
  -> DAYU 本机 MQTT Broker 下发设备指令
```

这里有两个非常重要的运行原则：

1. NLU 只输出结构化结果，不直接操作灯、空调、窗帘、门锁或报警器。
2. DAYU 与 ESP32 的设备通信走 DAYU 本机 Broker；PC Broker 只在上传数据和重新训练模型时使用。

## 4. 当前源码中的 NLU 入口

当前 DAYU 工程中与 NLU 直接相关的主要文件如下：

| 文件 | 作用 |
| --- | --- |
| `entry/src/main/ets/voice/VoiceAssistant.ets` | 语音助手主流程，负责 ASR 文本接入、意图解析调用、失败反馈和执行入口 |
| `entry/src/main/ets/voice/VoiceIntentParser.ets` | 规则解析器，承担短指令、常见表达、兜底解析和槽位抽取 |
| `entry/src/main/cpp/nlu_runtime.cpp` | 原生 NLU ONNX 推理入口，加载模型、Tokenizer 词表并返回分类结果 |
| `entry/src/main/ets/planner/PlannerAdapters.ets` | 将语音或 MLP 输出转换成 Planner 可识别的目标请求 |
| `entry/src/main/ets/pages/Index.ets` | 最终业务执行层，读取状态或下发控制命令 |
| `entry/src/main/resources/rawfile/voice/nlu/` | DAYU 端侧 NLU 模型、词表和相关资源 |

实际 `VoiceAssistant.resolveIntent()` 的顺序不是单纯“模型分类后直接执行”，而是：

```text
ASR 文本
  -> parseHardRule()
  -> VoiceIntentParser.parse()
  -> 如果仍 UNKNOWN 且 NLU 模型可用，则 classifyNlu()
  -> parseModelLabel()
  -> 槽位提取与范围校验
  -> 失败或不支持时回退规则解析
  -> Index.executeVoiceIntent()
```

这说明当前架构是“规则优先 + 模型增强 + 安全复核”的混合式 NLU，不是裸模型直接控制设备。

## 5. 数据集构建

当前用于扩展到规划器目标的 NLU 数据集位于：

```text
tools/nlu/data/hierarchical_v2_planner/
```

生成脚本和校验脚本为：

```text
tools/nlu/scripts/generate_hierarchical_dataset.py
tools/nlu/scripts/validate_hierarchical_dataset.py
```

数据集清单来自：

```text
tools/nlu/data/hierarchical_v2_planner/dataset_manifest.json
```

当前数据集总量为 4963 条，按用途划分如下：

| Split | 样本数 | 说明 |
| --- | ---: | --- |
| train | 3455 | 训练集 |
| validation | 486 | 训练过程中的验证集 |
| test | 512 | 普通离线测试集 |
| asr_noise_test | 386 | ASR 错字、漏字、近音字鲁棒性测试 |
| boundary_test | 24 | 温度、百分比等边界值测试 |
| safety_adversarial_test | 100 | 敏感操作、取消命令、未知输入等安全对抗测试 |

数据集采用 `expression_template_family` 划分策略，也就是按表达模板族隔离训练集、验证集和测试集。这样可以降低模板泄漏，避免训练集和测试集只是同一句话的轻微改写，导致指标虚高。

数据内容覆盖：

| 类型 | 示例 |
| --- | --- |
| 明确控制 | “打开客厅灯”、“把窗帘开到一半”、“空调调到 24 度” |
| 多表达同义句 | “帮我开灯”、“灯打开一下”、“把客厅灯打开” |
| 状态查询 | “窗帘现在开着吗”、“现在灯是开着的吗”、“空调是制冷还是制热” |
| 抽象需求 | “我有一点冷”、“我有一点热”、“我要睡觉”、“我要出门”、“我回家了” |
| ASR 噪声 | “客厅灯”被识别成近音或错字表达 |
| 取消和否定 | “不要开灯”、“刚才那句取消”、“别打开窗帘” |
| 敏感操作 | “打开门”、“解锁门” |
| 开放域 unknown | 与智能家居无关的问题或无法支持的表达 |
| 边界值 | 温度 16-30 度、窗帘 0-100% |

其中规划目标类数据通过 `goal` 槽位表达，例如：

```json
{
  "text": "我有一点冷",
  "intent": "comfort_warmer",
  "slots": {
    "goal": "comfort_warmer"
  }
}
```

当前数据集和 DAYU 运行时已经扩展到 20 个最终标签，其中 18 个为智能家居领域内意图，另外 2 个为安全和兜底标签。

| Intent | 功能 |
| --- | --- |
| `light_set` | 控制灯开关 |
| `ac_power_set` | 控制空调开关 |
| `curtain_set` | 控制窗帘开合或百分比 |
| `ac_temperature_set` | 设置空调温度 |
| `ac_mode_set` | 设置空调制冷或制热模式 |

查询类：

| Intent | 功能 |
| --- | --- |
| `light_status_query` | 查询灯是否开启 |
| `curtain_status_query` | 查询窗帘开合状态或百分比 |
| `ac_status_query` | 查询空调电源、温度或模式 |
| `door_status_query` | 查询门是否关闭或上锁 |
| `temperature_query` | 查询室内温度 |
| `humidity_query` | 查询室内湿度 |
| `environment_query` | 查询温湿度、烟雾、漏水等环境状态 |
| `alarm_status_query` | 查询报警状态 |

规划目标类：

| Intent | 功能 |
| --- | --- |
| `comfort_warmer` | 用户觉得冷，希望系统变暖 |
| `comfort_cooler` | 用户觉得热，希望系统变凉 |
| `sleep_scene` | 用户准备睡觉 |
| `away_scene` | 用户准备离家 |
| `home_scene` | 用户回家 |

| Label | 功能 |
| --- | --- |
| `requires_confirmation` | 涉及开门、解锁等敏感操作，需要额外确认，不直接执行 |
| `unknown` | 未知、取消、否定、不支持或开放域输入，不执行控制动作 |

## 7. 统一输出协议

NLU 对外输出应该统一为结构化对象，供执行器或规划器消费。典型字段如下：

| 字段 | 含义 |
| --- | --- |
| `intent` | 最终意图标签 |
| `confidence` | 模型或规则置信度 |
| `device` | 设备类型，例如 `light`、`curtain`、`ac`、`door` |
| `room` | 房间，例如 `living` |
| `power` | 电源状态，例如 `on`、`off` |
| `percentage` | 窗帘百分比，范围 0-100 |
| `temperature` | 空调温度，常规控制范围 16-30 |
| `mode` | 空调模式，例如 `cool`、`heat` |
| `queryAttribute` | 查询属性，例如 `power`、`percentage`、`temperature`、`mode` |
| `goal` | 抽象需求目标，例如 `comfort_warmer` |
| `rawText` | 原始 ASR 文本 |

查询窗帘状态的示例：

```json
{
  "intent": "curtain_status_query",
  "confidence": 0.96,
  "device": "curtain",
  "queryAttribute": "percentage",
  "rawText": "窗帘现在开着吗"
}
```

抽象需求的示例：

```json
{
  "intent": "comfort_warmer",
  "confidence": 0.94,
  "goal": "comfort_warmer",
  "rawText": "我有一点冷"
}
```

多条明确控制命令可以由 NLU 拆成顺序执行的多个结构化控制意图，例如：

```json
[
  {
    "intent": "light_set",
    "device": "light",
    "room": "living",
    "power": "on",
    "rawText": "打开客厅灯"
  },
  {
    "intent": "ac_power_set",
    "device": "ac",
    "power": "off",
    "rawText": "关闭空调"
  }
]
```

## 8. 模型设计

当前 NLU 采用分层 Transformer 分类架构，底座模型为：

```text
hfl/rbt3
```

它是中文轻量 RoBERTa 类预训练模型。选择它的主要原因是：中文能力较好、模型规模适合端侧、适合短文本分类、可以通过 PyTorch 微调后导出 ONNX。

分层结构可以理解为两步判断：

```text
第一层 route head:
  in_domain / requires_confirmation / unknown

第二层 intent head:
  在 in_domain 内进一步判断具体智能家居意图
```

这种设计比单纯做一个大分类头更适合本项目，因为它把“能不能执行”和“执行什么”拆开了。尤其是 `unknown` 和 `requires_confirmation` 需要更高安全性，不能和普通灯光、窗帘、空调控制混在一起只看最高概率。

当前训练仍采用“分类模型 + 规则槽位抽取”的方案。也就是说，Transformer 负责判断用户意图，设备、数值、模式等参数继续由确定性规则抽取并校验。这样比端到端生成 JSON 更稳定，也更容易解释和验收。

## 9. 训练过程

训练配置文件：

```text
tools/nlu/configs/hierarchical_planner_train_config.json
```

关键训练参数：

```json
{
  "base_model": "hfl/rbt3",
  "max_length": 48,
  "batch_size": 32,
  "eval_batch_size": 64,
  "epochs": 16,
  "learning_rate": 0.000015,
  "weight_decay": 0.01,
  "warmup_ratio": 0.1,
  "route_loss_weight": 1.5,
  "label_smoothing": 0.02,
  "early_stopping_patience": 5,
  "dropout": 0.1,
  "seed": 20260802
}
```

训练脚本：

```text
tools/nlu/scripts/train_hierarchical_classifier.py
```

脚本支持指定设备：

```text
--device cuda
--device cpu
--device auto
```

实际训练时建议显式使用 `--device cuda`。当前训练脚本已经避免在要求 CUDA 时静默退回 CPU，如果 GPU 环境不可用，应该直接报错并停止，避免出现“以为在 GPU 训练，实际在 CPU 慢慢跑”的情况。

训练产物通常包括：

| 产物 | 用途 |
| --- | --- |
| PyTorch checkpoint | 训练阶段保存最佳模型 |
| `vocab.txt` | 端侧分词词表 |
| `labels.json` 或标签配置 | 训练和运行时标签映射 |
| FP32 ONNX | 完整精度端侧候选模型 |
| Hybrid INT8 ONNX | 部分量化端侧部署模型 |
| 评估报告 | 记录 test、ASR、boundary、safety 指标 |


当前 DAYU 资源包中的主要模型文件为：

| 文件 | 大小 | SHA-256 |
| --- | ---: | --- |
| `hierarchical_nlu.fp32.onnx` | 151,684,312 bytes | `5b073abf5e7e0fe3a1b19d457d86bd88fc73bb9bc9ad29fc03a3eb2dfe61c9bd` |
| `hierarchical_nlu.hybrid_int8.onnx` | 109,260,658 bytes | `8df7ff6fe9a94805a03c9096437a7b56a5b0a8cfb7a6102927fdbac6a44b23e5` |
| `vocab.txt` | 109,540 bytes | `45bbac6b341c319adc98a532532882e91a9cefc0329aa57bac9ae761c27b291c` |

三个模型版本的含义：

| 模型 | 作用 | 部署建议 |
| --- | --- | --- |
| FP32 | 完整精度模型，质量最好，文件最大 | 作为质量基线和兜底模型 |
| Hybrid INT8 | 混合量化模型，保留 embedding 和 encoder layer 0 为 FP32，后续层动态 INT8 | 当前优先部署候选 |
| Full INT8 | 全量 INT8 实验模型，文件更小但质量下降明显 | 不建议部署 |

DAYU 端侧加载策略是优先尝试 Hybrid INT8，失败后尝试 FP32。如果两者都加载失败，系统应回退到原有规则解析器。

原生运行时使用 ONNX Runtime C API。工程中使用 ONNX Runtime v1.17.1 官方 C API 头文件声明，同时需要兼容 sherpa-onnx 运行库实际携带的 ONNX Runtime ABI。端侧最终是否稳定，还必须以 DAYU 真机验证为准。

## 12. NLU 功能清单

明确控制类支持用户直接控制设备。例如：

| 用户表达 | NLU 意图 | 后续动作 |
| --- | --- | --- |
| “开灯” | `light_set` | 打开客厅灯 |
| “关闭客厅灯” | `light_set` | 关闭客厅灯 |
| “打开空调” | `ac_power_set` | 打开空调 |
| “关闭空调” | `ac_power_set` | 关闭空调 |
| “空调调到 24 度” | `ac_temperature_set` | 设置空调温度 |
| “切换到制热模式” | `ac_mode_set` | 设置空调制热 |
| “窗帘打开一半” | `curtain_set` | 设置窗帘百分比 |

状态查询类读取 DAYU 当前状态，不应该播放固定“成功”提示冒充查询结果。例如：

| 用户表达 | NLU 意图 | 后续动作 |
| --- | --- | --- |
| “灯现在开着吗” | `light_status_query` | 查询灯状态 |
| “窗帘现在开着吗” | `curtain_status_query` | 查询窗帘状态或百分比 |
| “空调现在多少度” | `ac_status_query` 或 `temperature_query` | 查询空调或室内温度 |
| “现在是制冷还是制热” | `ac_status_query` | 查询空调模式 |
| “门是开着还是关着” | `door_status_query` | 查询门状态 |
| “有没有烟雾报警” | `alarm_status_query` | 查询报警状态 |

抽象需求类交给 Planner，不直接按固定动作硬编码。例如：

| 用户表达 | NLU 意图 | Planner 目标 |
| --- | --- | --- |
| “我有一点冷” | `comfort_warmer` | 让环境更暖 |
| “我有一点热” | `comfort_cooler` | 让环境更凉 |
| “我要睡觉” | `sleep_scene` | 睡眠场景 |
| “我要出门” | `away_scene` | 离家场景 |
| “我回家了” | `home_scene` | 回家场景 |

多条明确控制命令，例如“打开客厅灯，然后关闭空调”，属于语音 NLU 解析后的直接安全执行链，不经过联邦 MLP。它可以拆分成多条控制命令顺序执行。

## 13. 与规划器的关系

规划器解决的问题是：“当用户给出一个抽象目标时，系统应该怎样安全地完成它。”

例如：

```text
“我有一点冷”
  -> NLU: comfort_warmer
  -> Planner: 判断可以通过空调制热、调高温度、关闭窗帘等动作改善舒适度
  -> 安全执行链: 过滤禁止动作、校验参数范围、顺序执行允许工具
```

语音来源的规划目标在 `PlannerAdapters.ets` 中带有较高权限，例如 voice goal authority 为 90，source confidence 为 1。允许的工具包括：

```text
light.set
curtain.set
ac.set
```

明确禁止：

```text
door.open
door.close
door.lock
door.unlock
alarm write actions
```

这意味着门和报警状态可以查询，但门和报警的写操作不能由语音 NLU 或规划器直接控制。

明确控制和抽象需求的区别：

| 用户表达 | 走不走 Planner | 原因 |
| --- | --- | --- |
| “打开客厅灯” | 不走 | 用户已经明确指定动作，直接进入安全执行链 |
| “打开客厅灯，然后关闭空调” | 不走 | 多条明确动作，只需要拆分并校验 |
| “我有一点冷” | 走 | 用户说的是目标，不是具体设备动作 |
| “我要睡觉” | 走 | 用户说的是场景目标，需要生成动作计划 |

## 14. 与联邦 MLP 的关系

联邦 MLP 和语音 NLU 是两个不同入口：

| 模块 | 输入 | 输出 | 作用 |
| --- | --- | --- | --- |
| 语音 NLU | ASR 文本 | 结构化意图、槽位或 goal | 理解用户说的话 |
| 联邦 MLP | 家庭行为、时间、状态、传感器特征 | 抽象需求或建议 | 根据家庭习惯预测可能需要的场景 |
| Planner | NLU 或 MLP 给出的 goal | 安全动作计划 | 把目标变成可执行动作 |

联邦 MLP 不应该输出“直接打开某个设备”的裸命令，而更适合输出抽象需求，例如：

```json
{
  "source": "federated_mlp",
  "goal": "comfort_cooler",
  "confidence": 0.87,
  "context": {
    "indoorTemp": 29,
    "hour": 22,
    "homeOccupied": true
  }
}
```

然后 Planner 再结合当前设备状态和安全规则生成动作计划。

这样设计有两个好处：

1. 语音和联邦 MLP 可以共用同一个 Planner 与安全执行链。
2. 联邦 MLP 负责判断“可能需要什么”，Planner 负责判断“怎么执行才安全合理”。

当前用户明确语音控制的优先级最高。也就是说，如果用户刚说了“关闭空调”，联邦 MLP 的自动建议不能立刻反向打开空调。这个优先级约束应该在规划器或执行门控层体现，而不是靠 MLP 自己记住全部规则。

## 15. 安全执行链

安全边界是本项目最重要的工程原则之一。模型输出不能被当作最终授权。

必须坚持：

| 安全规则 | 说明 |
| --- | --- |
| 硬规则优先 | 敏感词、取消命令、门锁类操作先于模型判断 |
| 门和报警不可控制 | 门、报警允许查询状态，不允许由语音或 Planner 直接写操作 |
| 开门和解锁需要确认 | 进入 `requires_confirmation`，不得直接执行 |
| unknown 不执行 | 未知、开放域、不支持表达不得误接收成控制命令 |
| 取消命令不执行 | “别开灯”、“取消刚才那句”等不得转成正向控制 |
| 槽位范围复核 | 温度、百分比、模式等必须二次校验 |
| 模型失败可降级 | 模型加载或推理失败时回退规则解析器 |
| ONNX 裸模型不可独立部署 | 必须和硬规则、槽位校验、执行门控一起运行 |

安全对抗集重点检查以下错误是否为 0：

| 错误类型 | 含义 |
| --- | --- |
| unknown false accept | 未知输入被误接收 |
| unknown -> control | 未知输入被转成控制动作 |
| confirmation bypass | 需要确认的动作绕过确认 |
| cancelled command execution | 取消或否定命令被执行 |
| positive control block | 正常控制命令被错误拦截 |

## 17. 汇报时可以这样概括

本项目构建了一个“智能家居垂直领域大模型”，它基于中文预训练 Transformer 进行领域微调，能够在 DAYU 本地离线理解用户语音指令，将自然语言转换为智能家居结构化意图。系统采用分层意图分类、规则槽位抽取、安全对抗过滤和 Planner 规划执行的组合架构，既支持“开灯、关空调、查询窗帘状态”等明确指令，也支持“我有一点冷、我要睡觉、我回家了”等抽象需求。

与通用大模型不同，本模型不追求开放域聊天，而是追求智能家居场景中的可控、可解释、可端侧部署和可安全验收。语音 NLU 与联邦 MLP 共享后续规划器和安全执行链：语音负责理解用户明确表达，联邦 MLP 负责根据家庭习惯预测抽象需求，规划器负责把目标变成受约束的设备动作计划。

当前已有 v4 离线验收基线，Hybrid INT8 模型在离线测试中达到部署候选标准；DAYU 运行时和资源包已扩展到覆盖规划目标的 20 标签体系。下一步需要补齐 20 标签扩展版的完整离线验收报告和 DAYU 真机验证数据。
